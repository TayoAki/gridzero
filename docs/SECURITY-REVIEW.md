# Security review: agents and dashboards

Spec §12 lists what to review before inviting outside users. This records what was checked on
2026-11-10, how, and what changed as a result. "Test" names a test that now guards the point.

## Summary

| Area | Result |
|---|---|
| Cross-user access | Every agent, metric, dashboard, widget, proposal, schedule and approval route answers 404 for another user's resource. Tests: isolation cases in `tests/e2e/agents*.test.mjs`. |
| Key exposure | Keys are sealed at rest, never returned (only `last4`), never logged. Test: `agents.test.mjs` "key". |
| Private-data guard | Reading a sheet, query result, metric or app data removes web search and fetch for the rest of the run. Tests: `agents2`, `agents3`, `agents6`. |
| Approvals | Run the stored arguments, once, for the owner only. Tests: `agents6.test.mjs`. |
| Cost abuse | Monthly cap checked before every chat, approval follow-up, scheduled task and snapshot refresh; schedules limited in number and frequency (fixed in this review). |
| Destructive SQL from agents | Fixed in this review: agent SQL must be a single read statement. |
| Widget renderer | No raw HTML; links only `https://`. |
| Prompt injection | Mitigated by the guard, approvals and read-only schedules; residual risks listed below. |

## Findings

### 1. Agent SQL could change data on some warehouses (fixed)

`run_sql` was described as read-only, but nothing enforced it. Postgres and Redshift queries
already run inside a read-only transaction, so they were safe. Snowflake, Databricks and
BigQuery are only as read-only as the credentials saved, so a prompt-injected page could have
made an agent run `DELETE` or `DROP` there, including from a scheduled run.

Fix: `assertReadOnlySql` in `services/control/src/agents/workbook-tools.ts` rejects anything
but a single `SELECT`, `WITH`, `SHOW`, `DESCRIBE` or `EXPLAIN` statement, and any statement
containing a write keyword as a whole word. Metric SQL is generated by us and already
read-only. Users should still save warehouse credentials with read-only roles, as the README
already advises.

### 2. Schedules accepted any cron (fixed)

The UI only offers daily and weekly times, but the API took any 5-field cron, so a client
could schedule a task every minute and spend the whole monthly cap quickly. Fix: a schedule's
runs must be at least an hour apart (checked over its next runs), on top of the existing limits
of 20 schedules per user and 2 per widget.

### 3. Prompt injection: what remains

Content from web pages, cells and app data reaches the model as tool results. The system
prompt tells the model never to follow instructions found in tool results, but that is not a
guarantee. What an injected instruction could still do:

- **Write to the user's own workbooks** with `write_table` or `create_chart` in a chat run. Both
  only add (a new sheet, a new chart), never overwrite or delete, and only in workbooks the user
  can edit. Accepted for beta.
- **Send data out through a web request made before private data was read.** Once private data
  is read, web tools are gone for the rest of the run. Data read in an earlier run of the same
  chat is in the history, though, and a later run starts with web tools on again. Accepted for
  beta. To close it later, turn the guard on for the whole chat once any private tool has run in
  its history.
- **Ask for an app action that sends data out.** Every action that is not read-only needs the
  user's approval, and the card shows the exact arguments that will run.
- **Propose a widget with a link.** List links must be `https://` and open in a new tab with
  `noopener noreferrer`; the user has to click them.

### 4. SSRF

- `run_sql` uses the connections code, which refuses private and link-local addresses unless
  `CONNECTOR_ALLOW_PRIVATE=1` (tests only).
- `web_fetch` and `web_search` run on Anthropic's servers, not ours, so they cannot reach our
  network.
- The workbook host's `/agent` endpoint takes only a control-plane token and six allowed
  actions. Test: Rust `agent_tests` and `agents2.test.mjs`.

### 5. Approval replay and tampering

- Approve and refuse move the row from `pending` in one `UPDATE … WHERE status = 'pending'`,
  so a second approve gets 409 and runs nothing.
- The arguments that run are the ones stored when the agent asked; the browser cannot change
  them, and the model is not asked again.
- Approvals belong to the user whose agent asked; others get 404.

### 6. Key exposure

- Keys are sealed with AES-256-GCM (`encryptSecret`) and decrypted only inside the request or
  run that uses them.
- `GET /ai-key` returns provider, last four characters, cap and spend. Errors shown to users
  are fixed messages (spec §4.4); provider error text is logged, not returned. The error log
  records message, cause and stack, never request headers.

### 7. Widget renderer with hostile data

- Widget data is validated by the shared zod schema: lengths are capped, numbers must be
  finite, list links must start with `https://`.
- The renderer uses text nodes only; chat text turns only `https://` URLs into links. A
  `javascript:` URL fails validation and would not become a link anyway.

## Not covered yet

- A penetration test by someone other than the builder.
- A live check of the Composio integration with real OAuth apps.
- Rate limits per IP on the chat and approval routes beyond the per-agent busy check and the
  monthly cap.
