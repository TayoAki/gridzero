## Golden suite
- 180 cases across math, statistics, logic, text, lookup/reference, dynamic arrays and LAMBDA, date/time, financial, information and engineering ([tests/golden/s1_formulas.json](../../tests/golden/s1_formulas.json), generated by [gen_s1_cases.py](../../tests/golden/gen_s1_cases.py)).
- The cases include known Excel quirks, all of which IronCalc matched:
  - `=-2^2` is 4
  - `=ROUND(2.345,2)` is 2.35
  - the 1900 leap-year bug (`DATE(1900,3,1)` = 61)
  - `0.1+0.2`
  - `#DIV/0!`, `#N/A`, `#REF!`, `#NAME?` and `#VALUE!`
  - spill checks (`SEQUENCE`, `SORT`)
  - `XLOOKUP`, `FILTER`, `UNIQUE`, `LET`, `LAMBDA`, `MAP`.
- **The one failure:** `=TEXTJOIN("-",TRUE,"a","","b")` returns `a--b`, but Excel returns `a-b`. ignore_empty doesn't skip literal empty strings. This is a real compatibility bug; file it upstream and patch it in our fork.
- **Caveat:** expected values are hand-verified against documented Excel behaviour, and the financial and statistical values are computed from their closed-form definitions. No copy of Excel was available, so the M1 golden suite still needs real Excel-exported fixtures (BUILD-SPEC §13).
- IronCalc ships about 497 functions, well past the PRD's 400+ target.

| Scenario | Size | Time |
|---|---|---|
| Populate via `set_user_input` (parse) | 1M numbers + 1M formulas | 9.9–13.1 s |
| First evaluate | 1M formulas | 0.85 s |
| Recalc after editing one input | 1M independent formulas | 0.80–0.82 s |
| Recalc after edit, with `=SUM(B1:B1000000)` | 1M + 1 | 1.10–1.13 s |
| Dependency chain on a 2 MiB thread stack | depth 10k / 100k / 1M | 0.008 / 0.08 / 0.92 s, all correct |

## Findings that change the design
1. **Every `evaluate()` is a full recalculation.** Editing one cell in a 1M-formula sheet costs as much as the first evaluation (≈ 0.8 s), and IronCalc has no dirty-set tracking. That's fine up to roughly 1M formulas, but it puts the M1 "`UpdateCell` → patch ≤ 120 ms" budget at risk for large sheets.
2. **Parsing input is the slow path.** About 5–6 µs per `set_user_input`, so writing 5M rows × 7 columns (35M cells) into the grid would take about 3 minutes. That confirms the PRD's design: big imports must become **Data Tables (Polars/Arrow)**, not cells. "Import into cells" needs a row cap (proposed: 1M cells), or a bulk-load path that skips the formula parser for plain values.
3. **Deep chains are safe.** Recursion is bounded internally, so a 1M-deep chain evaluates on a 2 MiB stack without overflowing, which suits tokio worker threads.
4. **No serde on `Workbook`.** IronCalc uses `bitcode` (`Model::to_bytes`/`from_bytes`), so the snapshot is a MessagePack envelope that carries the IronCalc bytes as a binary field. This works, but the bitcode layout is tied to the IronCalc version, so snapshots must record the engine version and we need a migration path when we upgrade.
5. **One sheet value isn't Excel-identical** (TEXTJOIN, above). Expect a long tail of these; the compatibility-matrix process in BUILD-SPEC §13 covers it.

## Consequences (obligations on the M1 engine adapter)
- **A1 — Incremental recalc.** Build a dependency index in the adapter and recalc only the affected subgraph, by upstreaming dirty-tracking or patching our fork. Until then, keep cell-sheet formulas under 1M and debounce evaluation: batch the actions received in one tick, then evaluate once. Re-benchmark one-cell edits at 100k, 500k and 1M formulas in M1; the target is ≤ 50 ms at 100k.
- **A2 — Bulk value load.** Add a fork-level `set_value` fast path that skips the formula parser for imported constants. Cap "Import into cells" at 1M cells and send anything larger to a Data Table.
- **A3 — Snapshot versioning.** Add `engine: "ironcalc_base@0.9.1"` to the snapshot envelope, and write a CI test that loads snapshots produced by the previous engine version.
- Vendor `ironcalc_base` as a fork under `crates/ironcalc` in M1 (it stays a crates.io dependency for the spike), then fix TEXTJOIN and send the fix upstream.
